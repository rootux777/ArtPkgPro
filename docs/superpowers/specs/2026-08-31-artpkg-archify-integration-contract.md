# ArtPkg ↔ Archify Integration Contract

Date: 2026-08-31

Status: Draft for human review. **Integration is not authorized.** This document defines the contract only; it does not grant permission to wire ArtPkg and Archify together.

## Why This Document Exists

Both sides are now containerized and independently verified:

```text
ArtPkg container
  → 192.168.1.163:8555  (read-only status HTTP service, verified healthy)

Archify container
  → 192.168.1.163:8666  (read-only viewer, serves delivered static HTML)
```

Archify processing (`validate`, `deliver`, `visual-check`) is still a CLI/batch operation, not an HTTP API. Containerizing both sides does not change that. This document exists to state, precisely, what is allowed to cross the boundary between the two systems before any code changes are made.

This supersedes nothing in [2026-08-30-artpkg-archify-projection-design.md](2026-08-30-artpkg-archify-projection-design.md); it narrows that design to the concrete container topology and adds the custody/authorization rules needed now that both systems run as separate, network-reachable containers instead of local checkouts on one machine.

## Non-Negotiable Boundary

- ArtPkg is the only system that owns questionnaire state, requirements, authority, provenance, evidence states, validation gates, next permitted action, and human approval. ArtPkg is the **authority/state owner**.
- Archify is a **deterministic renderer + structural/schema validator**, and only that. A passing Archify `validate`/`deliver`/`visual-check` proves the diagram is structurally valid, schema-conformant, and visually deliverable. It proves nothing about package completeness, acceptance, governance approval, or safety to advance. Do not call Archify a "validator" without qualifying it as schema/render validation — unqualified "validator" invites later misreading as acceptance or governance validation, which it is not.
- If a custody/governance orchestrator (e.g. Pipeline-A) is introduced later, it owns invocation authorization and audit trail decisions; it is not defined by this document and this document grants it no authority by default.
- The Archify viewer container (`8666`) is read-only and serves already-delivered HTML. It is never a write path and never a trigger path.
- The ArtPkg status container (`8555`) is read-only status only (`/healthz`). It is not a generation or upload interface (per [container_deployment.md](../../container_deployment.md)) and it must not become an Archify trigger interface either.
- Archify has no HTTP API for `validate`/`deliver`/`visual-check` today. No component may fabricate one. If Archify later exposes a real HTTP API, that is a new, separately authorized design, not an extension of this contract.

### Authorization Invariant

```text
Projection materialization is not execution authorization.
Runner execution requires an explicit ArtPkg-owned invocation decision.
```

A file appearing in the shared projection custody area means only "a candidate input exists." It never means "the runner may act on it." The runner must not infer authorization from file presence, directory naming, timestamps, or any other filesystem signal. Authorization is a separate, explicit, ArtPkg-owned decision that the runner receives as an argument to its invocation, not something it discovers by scanning a directory.

## What ArtPkg Emits For Archify

ArtPkg emits exactly these files, generated by the existing `tools/artpkg_archify_projection.py` adapter, and nothing else:

```text
<view>.architecture.json          # Archify JSON IR (schema Archify accepts unmodified)
<view>.mapping.json               # ArtPkg semantic mapping sidecar (ArtPkg-owned, Archify never reads this)
<view>.projection-validation.md   # ArtPkg's own fail-closed projection report
```

Rules:

- ArtPkg must not modify Archify's IR schema to carry ArtPkg semantics. Anything Archify would ignore or reject belongs in the mapping sidecar, never in the IR.
- Every emitted IR file must be paired with a mapping sidecar recorded at the same time, referencing the same input digests (per the fail-closed rules already defined in the projection design doc).
- ArtPkg never emits partially seeded, unconfirmed, or `PROPOSED` answers into the IR as if they were `ACCEPTED`.

## Who Is Allowed To Invoke The Archify CLI

- Only `tools/artpkg_archify_runner.py`, invoked by an ArtPkg-owned process (operator CLI or the local intake UI backend) carrying an explicit invocation decision, may invoke the Archify CLI (`node bin/archify.mjs ...`). The runner is **the only writable integration actor** in this contract — no other component is permitted to write into the shared projection custody area or into Archify's working/output directories.
- The Archify container does not invoke itself, does not poll for new ArtPkg output, and does not pull from ArtPkg. All invocation is ArtPkg-initiated, one-shot, and explicit.
- No component may invoke Archify CLI commands over a network protocol. The runner must invoke a local Archify checkout/binary in the same execution context (same container, same host, or an explicit CI job) that can reach the input/output filesystem paths directly. Archify's `8666` container is not a valid invocation target — it has no CLI entrypoint exposed and is view-only.
- The read-only status service on `8555` must never gain a "trigger Archify" endpoint. If a future authorized design wants a button/endpoint for this, it needs its own review because it changes the read-only guarantee that container currently provides.

### Minimum Mount Permissions

The runner's execution context gets exactly the mounts it needs, no more:

```text
ArtPkg projection output (input/mapping/validation)  : read-only
Archify working/input area                           : writable only if a transformation step requires it
Archify output area                                  : writable
viewer output area                                   : same output path, mounted read-only by the viewer
```

Neither ArtPkg's status container (`8555`) nor the Archify viewer container (`8666`) may hold write access to any of these paths. Write access is scoped to the runner's own execution context only.

## Where Inputs/Outputs Cross The Boundary

Because Archify processing is CLI/batch, the crossing point is the filesystem, not a network call:

```text
ArtPkg authority/state
        │
        │ emits immutable projection bundle
        ▼
shared projection custody area
        │
        │ explicit ArtPkg-owned invocation
        ▼
artpkg_archify_runner.py
        │
        ├─ verify input hashes
        ├─ invoke Archify CLI
        ├─ capture exit/result
        ├─ hash outputs
        └─ write receipt
        ▼
Archify output directory
        │
        └─ mounted RO
             ▼
        viewer :8666
```

### Immutable Per-Attempt Run Directory

The crossing point is not a generic shared folder that gets overwritten in place. Each projection attempt gets its own identity:

```text
/integration/RUN-<id>/projection-001/
├── input/        # ArtPkg IR + source references for this attempt
├── mapping/       # ArtPkg mapping sidecar for this attempt
├── validation/    # ArtPkg projection-validation report for this attempt
├── output/        # Archify delivered HTML + delivery/visual-check results
└── receipt/       # runner receipt binding inputs to outputs (see below)
```

- Once `input/`, `mapping/`, and `validation/` are written for an attempt, they are treated as immutable for that attempt. The runner must not mutate them.
- A retry (different answers, different Archify invocation, re-run after a fix) creates a new attempt directory (e.g. `projection-002`), never overwrites `projection-001`. This keeps every prior attempt inspectable and keeps "what exactly produced this artifact" answerable without guesswork.
- `RUN-<id>` groups attempts that belong to the same review/package session; `projection-NNN` disambiguates attempts within that run.

For the current container topology, `/integration/` is a bind-mounted host path, analogous to the existing `/data/input` / `/data/output` contract in [container_deployment.md](../../container_deployment.md).

- ArtPkg container writes `input/`, `mapping/`, `validation/` into a new attempt directory (or a build step does, outside the read-only status container — the status container itself never writes here since it is read-only by design).
- The Archify CLI runner is the only actor that writes into `output/` and `receipt/`, from wherever it actually executes (developer machine, CI job, or a separate non-viewer Archify execution context with a writable mount — not the `8666` viewer container, which stays `read_only: true` like ArtPkg's own status container).
- The Archify viewer container (`8666`) only needs read access to `output/` to serve delivered HTML. It must not have write access and must not run the CLI.

This means today's two running containers (`8555` status, `8666` viewer) are **not** sufficient by themselves to run an end-to-end projection — neither one has both write access to a shared directory and the Archify CLI available. That gap is expected and correct: it keeps both containers minimal and read-only. Running an actual projection requires a separate, explicitly-authorized execution context (e.g., a CLI-capable Archify job with a writable mount to the attempt directory's `output/` and `receipt/` paths).

## How Review/Custody Is Preserved

- Every file crossing the boundary is content-addressed: SHA-256 digests of all inputs (`artifacts_package_answers.json`, validation report, optional package Markdown) are recorded in the mapping sidecar before projection, matching the existing fail-closed rule that "input package digests differ from the digests recorded in the sidecar" is a hard failure.
- Archify validation/delivery/visual-check results are never treated as ArtPkg gate evidence. A passing Archify delivery does not change ArtPkg's validation state, blocking answers, or next permitted action.
- Nothing served by the `8666` viewer is authoritative. It is a projection of a point-in-time ArtPkg snapshot; the projection-validation report and mapping sidecar are the only place claims about that projection's correctness live.

### Receipt Schema (Minimum Fields)

The runner records one receipt per attempt, binding the receipt to both the inputs and the outputs it produced, so "what exactly produced this artifact?" is always answerable later:

```text
ArtPkg IR SHA-256
mapping sidecar SHA-256
projection-validation SHA-256
Archify version
Archify image/CLI identity (if available)
output artifact SHA-256
invocation timestamp
exit code
runner version/hash
```

This extends, and does not replace, the fields `artpkg_archify_runner.py` already records (command, cwd, stdout/stderr, artifact/output digests) — the addition is binding explicit version/identity fields so a receipt is self-contained evidence of provenance, not just a debug log. Receipts are retained in the attempt's `receipt/` directory, never discarded.

### Staleness Is Deterministic, Not Inferred

The viewer must never imply freshness merely because an artifact exists at a path. Staleness is defined by one rule, not by ad hoc implementation behavior:

```text
A rendered artifact is stale if any authoritative input hash no longer matches
the receipt that produced it.
```

Concretely: before treating a delivered HTML as current, recompute the digest of the current authoritative ArtPkg output (answers JSON / validation report) and compare it to the input hash recorded in that attempt's receipt. A mismatch means the projection is stale and must be labeled as such wherever it is reviewed; it must never be silently served as current.

## Explicit Non-Goals For This Contract

- This contract does not stand up an HTTP bridge between ArtPkg and Archify.
- This contract does not make the `8555` or `8666` containers do anything beyond what they already do (read-only status, read-only viewing).
- This contract does not authorize building `artpkg_archify_projection.py` / `artpkg_archify_runner.py` into the container image or wiring them into `artpkg serve`.
- This contract does not change Archify schemas or give ArtPkg write access to the Archify checkout.
